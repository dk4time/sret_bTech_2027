1 · User and vehicles

rendering…

Why?

  • abstract class User Abstract, because there is no plain "user": it holds the shared data (id, name, phone, rating), so it is an abstract class, not an interface.
  • concrete class Customer Concrete class: a real person who books rides and has their own data (wallet, ride history).
  • concrete class Captain Concrete class: a real person who drives, with their own data (status, dues, acceptance rate).
  • enum CaptainStatus Enum: a fixed set of values (KYC_PENDING, OFFLINE, AVAILABLE, ON_RIDE), so an invalid status is impossible.
  • abstract class Vehicle Abstract: the fare formula is written once in the parent; each child overrides its own rates (polymorphism).
  • concrete class Bike Concrete: the cheapest vehicle; it supplies its own rates and speeds.
  • concrete class Auto Concrete: a three-wheeler with its own rates.
  • abstract class Cab Abstract, in the middle: it groups Economy and Premium and gives multilevel inheritance.
  • concrete class CabEconomy Concrete: a sedan cab (level 3 of Vehicle → Cab → CabEconomy).
  • concrete class CabPremium Concrete: an SUV cab with 6 seats.
  • enum VehicleType Enum: a fixed set of values (BIKE, AUTO, CAB_ECONOMY, CAB_PREMIUM), so an invalid value is impossible.

Captain HAS-A Vehicle: a captain is a person, not a vehicle, so this is composition (◆), not inheritance.

2 · Location and money

rendering…

Why?

  • concrete class Location Immutable: values never change, so it is safe to share one Location between many objects.
  • concrete class Money Immutable: values never change, so it is safe to share; it uses BigDecimal to avoid floating-point errors (₹0.1 + ₹0.2 is exactly ₹0.30).
  • concrete class ChennaiPlaces Concrete holder of named Chennai places (T. Nagar, Egmore…), created once as constants.
  • concrete class ServiceArea Concrete: the Chennai boundary, hotspots and congested zones; it rejects pickups or drops outside the city.

3 · Ride

rendering…

Why?

  • concrete class Ride Guards its own status: there is no setStatus(), only assignCaptain(), start(otp), complete(), cancel(). The OTP is private. This is the best encapsulation example.
  • concrete class Customer Shown here because a Ride has one (details in group 1).
  • concrete class Captain Shown here because a Ride has one (details in group 1).
  • enum RideStatus Enum: a fixed set of values (REQUESTED … COMPLETED, CANCELLED), so an invalid status is impossible.
  • concrete class FareReceipt The itemised bill. It is created for one ride and belongs to it (composition).
  • enum CancellationReason Enum: a fixed list of reasons, each allowed for only one party (customer, captain or system).

Ride HAS Customer and Captain: aggregation (◇), because both exist before and after the ride.

4 · Payments

rendering…

Why?

  • interface Payable Interface: no shared data, only a CAN-DO promise ("can pay"), so a new payment method is one new class and no changes to existing code.
  • concrete class UpiPayment Can-do Payable: pays by UPI; it can fail when the bank is down.
  • concrete class CashPayment Can-do Payable: the customer pays the captain in cash; it always succeeds.
  • concrete class WalletPayment Can-do Payable: pays from the in-app wallet, all or nothing.
  • enum PaymentStatus Enum: a fixed set of values (NOT_ATTEMPTED, SUCCESS, FAILED), so an invalid value is impossible.

Rule of thumb: abstract class = IS-A with shared data; interface = CAN-DO, no shared data.

5 · Notifications

rendering…

Why?

  • interface Notifier Interface: no shared data, only a CAN-DO promise ("can notify"), so adding WhatsApp or email is one new class.
  • concrete class SmsNotifier Can-do Notifier: sends a text message, but only for important events.
  • concrete class PushNotifier Can-do Notifier: sends an in-app push for every event.

RideService keeps a List<Notifier> and never asks "SMS or push?": the right code runs by itself (dynamic dispatch).

6 · Services

rendering…

Why?

  • concrete class CustomerService Services coordinate several objects; models enforce their own rules. This one registers customers and handles wallet top-ups.
  • concrete class CaptainService Registers captains, runs KYC, online/offline and dues settlement.
  • concrete class MatchingService Finds the nearest eligible captain and offers the ride.
  • concrete class RideService Runs the ride flow: book → assign → arrive → start → complete → pay.
  • concrete class FareService Calculates surge, estimates and the final receipt.
  • concrete class PaymentService Collects the money through a Payable.
  • concrete class RatingService Ratings for completed rides only, once per side.
  • concrete class EarningsService Splits every payment into captain earnings, commission and GST.
  • concrete class Customer Model class (group 1).
  • concrete class Captain Model class (group 1).
  • abstract class Vehicle Model class (group 1).
  • concrete class Ride Model class (group 3).
  • concrete class FareReceipt Model class (group 3).
  • interface Payable Model interface (group 4).
  • concrete class Location Model class (group 2).
  • concrete class Money Model class (group 2).
  • concrete class ServiceArea Model class (group 2).

Services coordinate several objects; the models handle their own rules (a Ride checks its own status, a Customer its own wallet).

7 · Clock and exceptions

rendering…

Why?

  • concrete class SimulatedClock Controlled time, so demos are repeatable and a night ride is one jump away.
  • concrete class Exception Java's own (JDK) checked exception class: the parent of our base exception.
  • concrete class RideHailingException Inheritance again: catch the parent to handle every app error, or a child to handle one specific error.
  • concrete class InvalidRideStatusException A ride method was called at the wrong moment (e.g. starting a cancelled ride).
  • concrete class InvalidOtpException The captain typed the wrong OTP.
  • concrete class NoCaptainAvailableException Nobody nearby accepted the ride.
  • concrete class CaptainNotEligibleException The captain cannot do this yet (e.g. KYC pending).
  • concrete class CaptainBusyException The captain is on a ride (e.g. cannot go offline).
  • concrete class InsufficientWalletBalanceException The wallet has too little money; nothing is deducted.
  • concrete class InvalidBookingException A booking rule was broken. It is the parent of the three booking errors below (multilevel).
  • concrete class ActiveRideExistsException The customer already has a ride in progress.
  • concrete class PaymentPendingException The customer must first pay for an earlier ride.
  • concrete class OutOfServiceAreaException The pickup or drop is outside Chennai.

Catch InvalidBookingException to catch all three booking errors at once, or RideHailingException for every app error.

8 · CLI (interactive mode)

rendering…

Why?

  • abstract class Menu Abstract: the menu loop is written once; each menu handles its choices differently.
  • concrete class StartupMenu Is-a Menu: demo / interactive mode / self-check.
  • concrete class MainMenu Is-a Menu: opens the other menus through Menu references (polymorphism).
  • concrete class CustomerMenu Is-a Menu: the customer's phone (book, cancel, pay…).
  • concrete class CaptainMenu Is-a Menu: the captain's phone (accept, arrive, OTP, complete…).
  • concrete class OperationsMenu Is-a Menu: the operations dashboard.
  • concrete class ClockMenu Is-a Menu: moves the simulated clock forward.
  • concrete class ConsoleIO All keyboard input and screen output, in one place.
  • concrete class CliSession The live world (a fresh seeded Chennai) behind the menus.

The menus contain no business rules: they only read input, call the services and print the result.

Notes on names and choices

  • Names: every type name was checked against the code (src/com/ridehailing/). All the names in the brief exist exactly as written, so nothing was renamed.
  • Added because it is in the code: StartupMenu (the 6th Menu subclass); InvalidBookingException with its three children ActiveRideExistsException, PaymentPendingException, OutOfServiceAreaException; Java's own Exception as the parent of RideHailingException; ConsoleIO and CliSession in the CLI group.
  • Ride has a Customer: in the code the Ride keeps its Captain directly and reaches its Customer through its RideRequest. Both are shown as aggregation (◇) because both people exist before and after the ride.
  • Links to enums (Captain → CaptainStatus, Ride → RideStatus / CancellationReason) are drawn as aggregation (“has-a, uses”), because an enum value is shared and is never owned by one object. Vehicle ..> VehicleType and Payable ..> PaymentStatus are dotted “uses” links: the type is returned by a method, not stored.
  • Location in group 2: ChennaiPlaces creates the named places (◆ owns); ServiceArea keeps shared references to some of them (◇ uses).
  • Services group: only the key model classes each service uses (from its imports) are drawn, so the picture stays readable.
  • Left out on purpose (see the detailed diagram docs/class_diagram.html): RideRequest, FareEstimate, OutstandingFee, TimelineEntry, PaymentMethod, RideEvent, NotificationLog, DispatchMode, RideAutopilot, ChennaiWorld, ChennaiRideApp, Launcher, GoBackException, QuitException, SelfCheck.
