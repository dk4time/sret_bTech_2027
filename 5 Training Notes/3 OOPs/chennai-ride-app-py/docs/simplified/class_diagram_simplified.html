Rapido Chennai — Simplified Class Diagram

Type names and relationships only. Built from the real ridehailing/ code. Rendering diagrams…

Arrows

ArrowNameLabelMeaning
Inheritance“is-a”Child IS-A parent and may override it. Solid line, hollow triangle.
Interface realisation“can-do”The class keeps the interface's promise. Dashed line, hollow triangle.
Composition“has-a, owns”Owns the part; the part lives and dies with it. Filled diamond ◆ at the owner.
Aggregation“has-a, uses”Refers to something that exists on its own. Hollow diamond ◇ at the holder.
Uses (dependency)“uses”Only in group 6: a service uses a model class. Dotted line, open arrow.

Colours

  • «abstract» abstract class: shared data, cannot be created
  • «interface» interface: a CAN-DO promise, no data
  • «enumeration» enum: a fixed set of values
  • Plain concrete class: real objects are made from it
  • «module» a Python module, not a class

Rule of thumb: abstract class = IS-A with shared data;
interface = CAN-DO, no shared data.

1 · User and vehicles

Rendering…

docs/simplified/diagrams/01_user_and_vehicles.mmd

Why?

  • User Abstract: no "plain" user exists. It holds shared data (id, name, phone, rating), so it is an abstract class, not an interface.
  • Customer Concrete: a real person who books, with their own data (wallet, ride history).
  • Captain Concrete: a real person who drives, with their own data (status, dues, vehicle).
  • Vehicle Abstract: the fare formula is written ONCE here; each child overrides its own rates (polymorphism).
  • Bike Concrete: overrides the rates with bike values.
  • Auto Concrete: overrides the rates with auto values.
  • Cab Abstract, in the middle: groups Economy and Premium, giving multilevel inheritance.
  • CabEconomy Concrete: Vehicle → Cab → CabEconomy (three levels).
  • CabPremium Concrete: Vehicle → Cab → CabPremium (three levels).
  • CaptainStatus Enum: a fixed set of values (KYC_PENDING, OFFLINE, ONLINE, ON_RIDE), so an invalid value is impossible.
  • VehicleType Enum: BIKE, AUTO, CAB_ECONOMY, CAB_PREMIUM, each with a seat count and a cancellation fee.

Captain HAS-A Vehicle: a captain is a person, not a vehicle, so this is composition (◆), not inheritance.

2 · Location and money

Rendering…

docs/simplified/diagrams/02_location_and_money.mmd

Why?

  • Location Immutable: a place never changes, so it is safe to share. Compared by value (same coordinates = equal).
  • Money Immutable: ₹ amounts never change. Decimal inside, so no floating-point errors (0.1 + 0.2 = 0.3 exactly).
  • chennai_places Not a class: a module holding a dict of real Chennai places and helper functions. Location.from_place_name() reads it.
  • ServiceArea Concrete: the Chennai Metro box. A pickup or drop outside it is rejected.

These are small building blocks used everywhere. They only appear as parameters of each other, so this group has no arrows.

3 · Ride

Rendering…

docs/simplified/diagrams/03_ride.mmd

Why?

  • Ride Guards its own status: there is no set_status(), only assign_captain(), start(otp), complete(), cancel(). The OTP is private. The best encapsulation example.
  • Customer Aggregation: the customer exists before and after the ride.
  • Captain Aggregation: the captain exists before and after the ride.
  • RideRequest Composition: what was booked (pickup, drop, vehicle type), frozen at booking.
  • FareEstimate Composition: the price shown before confirming.
  • FareReceipt Composition: the itemised bill, created for this ride only.
  • RideStatus Enum: REQUESTED → … → COMPLETED / CANCELLED. Only these values can exist.
  • CancellationReason Enum: CUSTOMER_CANCELLED, NO_SHOW, OTP_FAILED, NO_CAPTAIN_AVAILABLE.

◇ (aggregation) = the ride only refers to them. ◆ (composition) = the ride owns them.

4 · Payments

Rendering…

docs/simplified/diagrams/04_payments.mmd

Why?

  • Payable Interface: shares no data, only a CAN-DO promise (pay). A new payment method = one new class, no changes to existing code.
  • UpiPayment Can-do pay(): UPI, which can fail (seeded, so every run is identical).
  • CashPayment Can-do pay(): cash, which always succeeds; the captain then owes the platform its share.
  • WalletPayment Can-do pay(): wallet, which deducts all or nothing, never partially.
  • PaymentStatus Enum: NOT_DUE, FAILED, PAID, so a ride's payment can only be in one of these states.

Rule of thumb: abstract class = IS-A with shared data; interface = CAN-DO, no shared data.

5 · Notifications

Rendering…

docs/simplified/diagrams/05_notifications.mmd

Why?

  • Notifier Abstract class in the code (not an interface): it keeps shared data, the log of sent messages. By the rule of thumb (shared data), that makes it abstract.
  • SmsNotifier Is-a Notifier: sends by SMS to the user's +91 number.
  • PushNotifier Is-a Notifier: in-app push (printed in the demo).

RideService holds a list of Notifier and calls notify() on each, without knowing SMS from push. That is polymorphism.

6 · Services

Rendering…

docs/simplified/diagrams/06_services.mmd

Why?

  • CustomerService Registers customers, tops up wallets, moves customers around.
  • CaptainService Registers captains with their vehicles; online/offline; settles dues.
  • MatchingService Finds the nearest eligible captain for a ride.
  • RideService Runs every ride flow, from booking to payment, and notifies on each event.
  • FareService All fare maths: rates, surge, night charge, coupon, receipt.
  • PaymentService Takes payment through any Payable and keeps a ledger.
  • RatingService Ratings after COMPLETED rides only.
  • EarningsService Splits money into captain earnings, commission and GST; proves the books balance.
  • Ride Model: see group 3.
  • Customer Model: see group 1.
  • Captain Model: see group 1.
  • Vehicle Model: see group 1.
  • Location Model: see group 2.
  • Money Model: see group 2.
  • FareReceipt Model: see group 3.
  • Payable Model: see group 4.
  • Notifier Model: see group 5.

Every dotted arrow means USES. Services coordinate several objects; models handle their own rules. The arrows show the main model classes each service imports.

7 · Clock and exceptions

Rendering…

docs/simplified/diagrams/07_clock_and_exceptions.mmd

Why?

  • SimulatedClock Controlled time: repeatable demos, and night rides on demand. It can never go backwards.
  • Exception Python's built-in base class for all errors.
  • RideHailingError Inheritance again: catch the parent to handle ALL app errors…
  • 17 specific errors …or catch one child for one specific error, e.g. InsufficientWalletBalanceError.

Catch RideHailingError → every app error. Catch InvalidOtpError → just that one.

8 · CLI

Rendering…

docs/simplified/diagrams/08_cli.mmd

Why?

  • Menu Abstract: the show/read/handle loop is written ONCE; each menu handles its choices differently.
  • StartupMenu Is-a Menu: demo / interactive mode / self-check.
  • MainMenu Is-a Menu. It also owns its four sub-menus and holds them as Menu (polymorphism).
  • CustomerMenu Is-a Menu: the customer's phone app.
  • CaptainMenu Is-a Menu: the captain's phone app.
  • OperationsMenu Is-a Menu: the operations dashboard.
  • ClockMenu Is-a Menu: move the clock forward.
  • ConsoleIO One shared object for all input and output (aggregation: every menu uses the same one).

The CLI has no business rules; it only calls the services in group 6.

9 · Overview: how the groups connect

Rendering…

docs/simplified/diagrams/09_overview.mmd

Why?

  • Ride → User group: A ride refers to one Customer and one Captain (aggregation).
  • Ride → Payments: A ride is paid through a Payable: UPI, cash or wallet.
  • Services → models: Services coordinate; the model classes keep their own rules.
  • CLI → Services: Menus only call services, so the same objects power the demo and the CLI.

Group 6 (services) is the hub: it connects the models to each other and to the CLI.

Notes: where the names differ from the brief

ChennaiPlacesThe code has no ChennaiPlaces class. It is the module chennai_places (a dict of places plus helper functions), shown as a dashed «module» box.
Notifier «interface»In the code Notifier is an abstract class (abc.ABC) that stores the sent-message log and has a concrete _record() method, so it is marked «abstract», not «interface».
Payable «interface»Python has no interface keyword. Payable is an ABC used as an interface: both of its members are abstract, plus one default property, is_cash.
setStatus(), assignCaptain()The code is Python, so its names are snake_case: assign_captain(), start(otp), complete(), cancel(). There is no set_status() at all.
Base exception classThe base class is RideHailingError (in ridehailing/exceptions.py), which itself extends Python's Exception.
Extra types shownThe code also has these types, included because they belong to the groups: RideRequest and FareEstimate (group 3), ServiceArea (group 2), StartupMenu and ConsoleIO (group 8).
Not shownHelper classes left out to keep it simple: PendingFee, DailyEarnings, PaymentRecord, ChennaiRideApp, CliSession, and the CLI control exceptions GoBack / QuitRequested / EndOfInput. The detailed diagrams are in docs/class_diagram.html.
